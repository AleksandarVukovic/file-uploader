# 1. mTLS between internal services

## Status

Accepted

## Context

`api-service` is the only publicly exposed service; it forwards uploads to
`file-service` over plain HTTP. `infra/` has no Terraform, Kubernetes, or
service mesh yet, so there is no network-layer control (NetworkPolicy, mesh
sidecar mTLS, etc.) restricting who can call `file-service`'s internal API.
As more internal services are built out (`user-service`,
`file-processing-service`), the same gap will apply to their
service-to-service calls too.

## Decision

Protect internal service-to-service HTTP calls with always-on, mutual TLS
at the application layer, starting with the api-service → file-service
upload call:

- Each internal endpoint that should only be reachable by other services
  (e.g. file-service's files API) runs on its own TLS listener requiring
  and verifying a client certificate (`tls.RequireAndVerifyClientCert`).
  Endpoints reachable by infra without a client certificate (e.g.
  `GET /health`, probed by kubelet) stay on a separate plain-HTTP listener.
- Certificates are issued by a single local, self-signed development CA,
  generated by `scripts/gen-dev-certs.sh` (`make certs`) and mounted into
  containers via `docker-compose.local.yml`. Nothing under the generated
  `certs/` directory is committed. `file-service`'s mTLS integration tests
  consume these same real dev certs rather than generating their own
  in-memory — `make certs` is a required step before
  `make test-integration` for `file-service`.
- Shared TLS config building lives in `common/tls`.
- There is no plaintext fallback — once a service's client/server TLS
  config is wired up, that connection always uses mTLS.

Production certificate issuance, rotation, and revocation (Vault,
cert-manager, a service mesh, etc.) is explicitly deferred — it depends on
infrastructure (`infra/`) that doesn't exist yet, and will be its own ADR
once that infrastructure is designed.

## Consequences

- Local development and file-service's own integration tests require a
  valid cert/key/CA on disk, generated by `make certs`; a missing or
  invalid one fails fast at startup/test time rather than silently
  running in plaintext.
- Services that need an mTLS-protected internal endpoint run two listeners
  (one plain, one mTLS) instead of one, each with the handler scoped to
  only the routes appropriate for that trust level.
- `user-service` and `file-processing-service` are expected to adopt the
  same pattern (dedicated mTLS listener for internal endpoints, local dev
  CA for now) once they're built out, rather than inventing a new
  approach per service.
- This ADR does not resolve certificate rotation or production issuance;
  a follow-up ADR is required before this pattern is relied on outside
  local development.
